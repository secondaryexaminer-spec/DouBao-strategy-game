## 一、金帐本轮实现的硬依赖（3 项）

### GH-01 `productionCompleted` 实际埋点

- **当前代码证据位置**：契约 §2.2 声明该事件；`factionRegistry.js:12-24` 有 `onProductionCompleted → 'productionCompleted'` 映射；但 main.js 全部 8 处 `eventBus.emit`（828/844/896/947/1001/1141/1183/1221）中**不存在** productionCompleted。唯一生产路径 `buildAtSite`（main.js:1479-1502）未 emit。
- **不补会造成的问题**：契约声明的钩子 `onProductionCompleted` 是休眠钩子，任何系统都无法感知"生产完成"；金帐营地生产的完成通知无从挂载；后续威尼斯（商队/造船）、大明（生产联动）同样受堵。
- **推荐 API 名称和参数**：在 `buildAtSite` 成功分支（main.js:1491-1501，`game.units.push` 之后）emit：
  ```js
  eventBus.emit('productionCompleted', { owner, unit, site, kind: 'unit'|'ship' })
  ```
  与契约 §2.2 定义一致（`{owner, unit?, site?, kind}`）；`buildCamp`（main.js:1562-1573）如需覆盖营地建立可追加 `kind:'camp'`，金帐本轮不依赖。
- **影响范围**：HRE 不监听该事件（hreRules.js 无此钩子）→ **无回归**；威尼斯/大明未来生产联动受益；马穆鲁克经验来源走 unitKilled，不受影响。
- **是否本轮阻塞**：**是**（营地生产依赖；同时修复契约声明与实现的缺口）。

### GH-02 安全的单位创建/生产能力（ctx.createUnit）

- **当前代码证据位置**：`factionContext.js` 无任何单位创建能力；`unit()` 工厂在 main.js:519-539 闭包内；`buildAtSite`（main.js:1479）是唯一生产路径，且仅接受 **site**（营地是 facility 不经过它）；`game` 在 ctx 中是"只读引用"（契约 §5）。
- **不补会造成的问题**：金帐营地生产（facility 型营地）在架构内无 sanctioned 方式产出单位；若用 `game.units.push` 手工构造单位，违反契约 §5 边界、跳过 id 生成/统计/日志，且与既定决定"营地生产不能用 game.units.push 或直接 import core 绕过架构"冲突。
- **推荐 API 名称和参数**（追加到 FactionContext，契约 §5）：
  ```js
  createUnit(type, owner, x, y, opts?) -> unitEntry
  // 内部委托 main.js 闭包 unit() 工厂（main.js:519-539），保证 id/字段与主流程一致
  // 可选：incrementStat('produced', 1)；若将来补 unitCreated 埋点则由工厂 emit
  ```
- **影响范围**：无既有系统依赖 → 无回归；公共能力，威尼斯商队、大明工程师部署等后续可用。
- **是否本轮阻塞**：**是**（营地生产的唯一合规通道）。

### GH-03 `tickStatuses` 统一接线与调用时机

- **当前代码证据位置**：`status.js:35-48` 已实现 `tickStatuses(aliveUnitIds)`，但 main.js **从未调用**（grep 仅 status.js 自身）；契约 §3.1 写的签名是 `tickStatuses(owner)`，与实际实现不一致；main.js beginTurn（1148-1204）中 healOwner→grantIncome→emit turnStart（1183）→移动重置循环（1184-1189）。
- **不补会造成的问题**：`raided`（turns=1）**永远不会过期**；状态系统成为摆设；马穆鲁克 ambush、大明 crossfire（契约 §3.1 预设 key）未来全部踩同一个坑。
- **推荐 API 与调用时机**：
  ```js
  // main.js beginTurn 内、eventBus.emit('turnStart') 之前（1183 行前）：
  statusSystem.tickStatuses(game.units.filter(u => u.owner === owner).map(u => u.id));
  // 同时把契约 §3.1 签名更正为 tickStatuses(aliveUnitIds)
  ```
  两个关键约束（请主对话务必按此接线）：
  1. **必须在 `turnStart` emit 之前**：否则 HRE 在 onTurnStart 里新加的 `frontline`（turns=1，fortification.js:260）会被紧随的 tick 立刻清掉 → 状态永远留不住，产生回归。
  2. **tick 只作用于当前 owner 存活单位**（按 aliveUnitIds）：金帐 raided 会以 `turns=2` 写入（金帐模块侧定值）——敌方回合 tick→1（该回合移动-1 全程生效），金帐下轮攻击时标记仍在（叠加收益生效），再下轮归零。这正好满足"持续 1 回合 + 继续被金帐攻击额外收益"的规格书语义。
- **影响范围**：HRE 有 `frontline` 状态（唯一既有 status 使用者）——按上述时机接线**无回归**；马穆鲁克/大明未来依赖；金帐本轮硬依赖。
- **是否本轮阻塞**：**是**。

## 二、本轮可以降级（2 项，均写入交付报告"已知问题"）

### GH-04 raided 对回血的限制

- **当前代码证据位置**：`healOwner`（main.js:1112-1128）在 beginTurn 内**先于** `turnStart` emit（1183）执行；回血量在闭包内算好直接加血（main.js:1124），无任何事件或可干预点。
- **不补会造成的问题**：金帐 onTurnStart 触发时回血已完成，且无法得知实际回血量，架构内无法实现"raided 回血减半/失效"。
- **推荐 API**（供后续补齐，本轮不做）：
  ```js
  eventBus.emit('beforeHeal', { owner, unit, amount })   // amount 可改，参考 incomeCalculated 模式
  // 位置：healOwner 实际加血（main.js:1124）之前
  ```
- **影响范围**：healOwner 覆盖基础回血路径；HRE 石堡/阵线回血不经 healOwner（fortification.js 在 onTurnStart 自行加血）→ 不受影响；巴伐利亚 +1 在 healOwner 内；白帐绿洲回血（阶段3）未来受益。
- **是否本轮阻塞**：**否**（降级：raided 效果收窄为"移动-1 + 叠加收益"，规格书 §5.2 允许自行定效果组合，交付报告注明）。

### GH-05 camp/补给摧毁奖励

- **当前代码证据位置**：`captureSite` 的 camp 分支（main.js:926-936）直接移除营地并 `return`，**不 emit 任何事件**（siteCaptured 在非 camp 分支 947 行才 emit）。
- **不补会造成的问题**：金帐"摧毁敌方补给/营地 +4 金币"（规格书 §5.1）无钩子可挂；营地被摧毁也无法统计/联动。
- **推荐 API**（供后续补齐，本轮不做）：
  ```js
  eventBus.emit('siteDestroyed', { site, destroyer, oldOwner })   // 或按 siteCaptured 对称：{ unit, site, oldOwner }
  // 位置：captureSite camp 分支移除后、return 前（main.js:935）
  ```
- **影响范围**：无既有依赖 → 无回归；公共能力，阶段3 绿洲网络/中立商港等可能用。
- **是否本轮阻塞**：**否**（降级，交付报告注明）。

## 三、后续建议补齐的公共能力（4 项）

### GH-06 `beforeHeal` / heal Hook

同 GH-04（推荐 API 与位置见上）。作为公共能力建议纳入契约 §2.2 事件清单，理由：healOwner 是唯一回血主路径，任何"减疗/增疗"类机制（金帐 raided、阶段3 绿洲网络、马穆鲁克精英）都缺挂点。**非本轮阻塞**，影响 HRE/白帐/巴伐利亚等回血相关机制，属公共增益。

### GH-07 `siteDestroyed` / `campDestroyed` 事件

同 GH-05。作为公共能力建议纳入契约 §2.2，与 `siteCaptured` 对称。**非本轮阻塞**，影响阶段3 及所有"据点被摧毁"类联动。

### GH-08 `getStatus` / `getAllStatuses` 经 ctx 暴露

- **当前代码证据位置**：`factionContext.js:30` 只有 `hasStatus(unitId, key)`；`status.js:26-34` 已实现 `getStatus`/`getAllStatuses` 但未在 ctx 转发；契约 §5 未列出。
- **不补会造成的问题**：联盟系统无法读取状态剩余 `turns` 和 `data`（如显示 raided 剩余、ambush 的 data 参数）；只能"有/无"判断。
- **推荐 API**（契约 §5 追加两行，直接转发 statusSystem）：
  ```js
  getStatus(unitId, key) -> {key, turns, data} | null
  getAllStatuses(unitId) -> array
  ```
- **影响范围**：纯查询转发，无回归；所有联盟通用。
- **是否本轮阻塞**：**否**（金帐用 hasStatus 即可闭环）。

### GH-09 `unitKilled` payload 与契约对齐

- **当前代码证据位置**：main.js:828 `emit('unitKilled', { victim, killer: null, reason: 'removeUnit' })`，与契约 §2.2 `{ killer, victim, context: 'attack'|'splash'|'counter'|'other' }` **字段名不一致**（reason vs context）；killer 恒为 null。
- **不补会造成的问题**：击杀归因不可能；马穆鲁克"精英阵亡代价"、阶段3 可汗威望（击杀计数）依赖 killer/context 时会踩坑；契约文档与实现长期漂移。
- **推荐 API**：实现向契约对齐（改三处攻击击杀埋点为 `{ victim, killer, context }`，已约定由主对话统一改），或契约向实际对齐（`reason` 字段）。二选一，主对话定。
- **影响范围**：当前无订阅者依赖（HRE 不监听 unitKilled）→ 无回归；马穆鲁克/金帐阶段3 依赖。
- **是否本轮阻塞**：**否**（金帐本轮用 afterAttack.defenderDead，已规避）。
