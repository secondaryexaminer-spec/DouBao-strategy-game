## 2. GH-02 ctx.createUnit 生产能力（实施）

- **文件**：`src/factions/factionContext.js` + `src/main.js`（initFactionSystems 的 deps）
- **关键点**：单位工厂 `unit()` 与 `randomId()` 都在 main.js 闭包内，factionContext.js 无法 import → **createUnit 必须由 main.js 经 deps 注入**，factionContext 只做转发。这与 getUnit/log 等现有 deps 模式一致。
- **main.js deps 注入**（initFactionSystems 内新增）：
  ```js
  createUnit: (type, owner, x, y) => {
    if (!typeMeta(type)) return null;            // 防御：无效类型
    const created = unit(type, owner, x, y);      // 复用主流程工厂：randomId/字段完全一致
    game.units.push(created);                     // 唯一合规入数组通道（对齐 buildAtSite）
    incrementStat('produced', owner, 1);          // 统计口径与 buildAtSite 一致
    return created;
  },
  ```
- **ctx 转发**（factionContext.js）：
  ```js
  createUnit: (type, owner, x, y) => deps.createUnit(type, owner, x, y),
  ```
- **职责边界**：createUnit = 底层工厂（创建+入数组+统计）。金币/上限/营地状态校验 = 业务逻辑，由金帐模块在调用前自查；日志由金帐模块用 ctx.log 自打。**不做**金币/上限校验（避免把业务耦合进工厂）。
- **不 emit unitCreated**：契约已定义但 main.js 全部生产路径（buildAtSite/征召兵/卫所制/登陆）均未埋；只在 createUnit 里半埋会造成事件语义不一致。**unitCreated 列入后续排期**（与 GH-06~09 一起，主对话统一补全部生产路径）。
- **HRE 影响**：无（新增能力，HRE 不使用）

## 3. GH-03 tickStatuses 统一接线（实施，含 1 处方案修正）

### 3.1 接线

- **文件**：`src/main.js` → `beginTurn`
- **位置**：`if (!initial) {` 块**之前**（1159 行前；比申请单建议的"1183 turnStart emit 前"更早，语义为"回合开始时先衰减全部状态，再执行回血/收入/生产/征召"；同样满足"必须早于 turnStart emit"这一防 HRE 回归约束）
- **调用**：
  ```js
  statusSystem.tickStatuses(game.units.map(u => u.id));
  ```
- **申请单方案修正（重要）**：申请单建议 `tickStatuses(该 owner 存活单位 id 列表)`。**这有 bug**——status.js 的 `tickStatuses` 对"不在 aliveUnitIds 列表"的单位状态执行**删除**（status.js:39-41）。若只传当前 owner 单位，**其他 owner 存活单位的状态会被误删**（如神罗单位身上的 raided 会在金帐回合被删掉，额外收益永远失效）。**必须传全量存活单位**：`game.units.map(u => u.id)`。

### 3.2 语义确认（对应申请单"请主对话确认"的问题）

- **状态何时施加**：金帐 `afterAttack` 中（defenderDead=false 时）`addStatus(X, 'raided', turns, data)`。
- **何时第一次 tick**：施加后的**下一个 beginTurn**（任意方，含敌方回合开头）。
- **调用频率**：**每 beginTurn 一次**（每个 owner 回合一次；2 人局每全局 turn 2 次，3 人局 3 次）。
- **raided 写 turns 的推导**（tick 频率=每 beginTurn、全量）：
  | 写入值 | 敌方回合 tick 后 | 金帐下轮攻击时 | 结论 |
  |---|---|---|---|
  | turns=2 | 剩 1（移动-1 生效 ✅） | **已被金帐回合 tick 清 0，额外收益失效 ❌** | 不够 |
  | turns=3 | 剩 2（移动-1 生效 ✅） | 金帐回合 tick 后剩 1，**额外收益生效 ✅** | 正确 |
- **结论**：**金帐 raided 写 `turns=3`**（不是 2）。玩家可见语义：
  - "持续 1 回合" = 敌方**恰好 1 个完整回合**移动受限（turns 3→2 与 2→1 两段均覆盖该敌方回合）；
  - 额外收益窗口 = **下一个金帐回合攻击时**（turns=1 残留）；
  - 金帐交付报告中必须解释 `turns=3` 与玩家可见"持续 1 回合"的关系（本方案作为契约确认结论写入）。
- **HRE 影响（无回归）**：HRE 是唯一既有 status 使用者（`frontline` turns=1，fortification.js:260 每回合 onTurnStart 重建）。tick 在每个 beginTurn 开头先清上一轮 frontline，随后 turnStart → HRE onTurnStart 重新 addStatus → 当回合全程有效，下回合开头再清。**先清后加，语义正确，无回归**。harness 不受影响（harness 模拟 turnStart 不调 main.js 的 tick）。
